# Worker 자원 제한과 경기 타임라인 — 2026-09-08

## 조사 결과

이전 `stepMatch`는 요청마다 generator를 다시 만들고 1회부터 현재 타석까지 실행했다. N개 타석을 보는 동안 누적 실행은 O(N²)이었으며 완료 시에도 같은 경기를 재계산했다. 엔진 생성 때 여러 `createGameView`가 전 세계 선수 명단을 복사했고, `/api/catalog`에서도 커리어 전체를 읽고 보정했다. SSR은 경기 엔진을 호출하지 않았지만 공통 Worker의 정적 API import가 NestJS 초기화를 함께 실행했다.

무한 경기 반복이나 대량 `Promise.all` 팬아웃은 확인되지 않았다. 기존 이닝·타석·Poisson·일정 편성에는 상한이 있었으며, 남은 병렬 처리는 카탈로그/설정 조회 등 고정 개수다. 추가로 generator 소비를 1,200이벤트에서 중단하고 경기 계획 변경은 40회로 제한한다.

Cloudflare는 CPU와 메모리 초과에 1102를 반환할 수 있다. Free의 HTTP CPU 한도는 10ms, Paid 기본은 30초이며 네트워크/DB 대기 시간과 CPU 시간은 다르다. 요금제나 CPU 제한을 임의로 변경하지 않았다. [공식 자원 제한 안내](https://developers.cloudflare.com/workers/platform/limits/)

확인 가능한 기존 비공개 Sites의 최근 오류 로그에는 인증 401이 있었고 `exceededCpu`/`exceededMemory`인 해당 사용자 요청은 확보하지 못했다. 따라서 발견한 비효율 제거와 실제 오류 발생 요청의 원인 확정을 구분한다. 공개 Worker의 발생 URL·동작·Ray ID/시간이 확보되면 Workers invocation의 CPU·wall time·outcome과 대조해야 한다.

## 변경된 처리

1. `startMatch`: 동결한 입력으로 **한 경기**의 최종 결과·타석별 before/after·성적 반영분을 생성하여 기존 D1 커리어 JSON에 저장한다. 진행 날짜·성적·예산은 아직 반영하지 않는다.
2. 브라우저: 저장된 이벤트를 순서대로 읽고 위치/프레임만 재생한다. 득점·타격·투구 결과를 계산하지 않으며 타석마다 POST하지 않는다. 타구·주자의 보간은 화면 연출이다.
3. `reviseMatch`: 프리뷰는 새 타순/선발/전술로, 진행 중에는 기록한 변경 지점 이후의 지시로 한 경기를 다시 준비한다. 이미 소비한 이벤트를 새 prefix와 비교하고 일치할 때만 저장한다. 투수는 수비 직전에 교체하며, 벤치 선수 교체와 팀 지시를 지원한다. 타순 재배열과 재출전은 경기 중 거부한다.
4. `completeMatch`: 저장된 성적 반영분과 결과를 커리어·경기 아카이브에 한 번 반영한다. 같은 경기를 다시 시뮬레이션하지 않는다. revision과 requestId, D1 원자적 저장은 유지한다.

`LiveMatch.prepared`와 동결된 상대 선수 입력은 서버 전용이다. 출력에서 제거한다. `timeline`에는 완성된 이벤트가 전달되지만 화면은 소비한 이벤트와 현재 점수만 표시한다. 미래 결과를 네트워크 분석에서도 숨기는 모델은 아니다.

재생 위치는 현재 기기의 localStorage에 저장한다. 일반 재생 중 서버 쓰기를 없앴으므로 다른 기기에서 마지막 프레임까지 이어가는 기능은 제공하지 않는다. 서버의 cursor는 명시적 위치 명령·계획 변경 때 검증·저장되고 완료에도 사용한다. 다른 화면에서 서버 상태가 바뀌면 revision/타임라인 버전 검증으로 변경을 거부한다. 타석별 실시간 서버 동기화라고 설명하면 안 된다.

이전 미완료 경기는 GET/SSR에서 시뮬레이션하지 않는다. 사용자의 `prepareMatch` 또는 호환 명령으로 한 번 준비한다. 저장 당시 투수 규칙 버전과 seed를 유지하며 구버전 결과 해시 회귀를 통과한다. SQL 스키마 변경·DB 초기화는 없다.

## 그 외 CPU 절감

- API를 동적으로 불러오고 NestJS HTTP bridge를 API 요청 때 초기화한다. SSR/정적 요청은 API 초기화를 실행하지 않는다.
- `/api/catalog`은 공개 잠재력 설정만 SQL로 읽는다. 불변 카탈로그의 숨김 출력·구단/리그/선수 인덱스를 재사용한다. 사용자별 선수단이나 일정은 전역 캐시로 공유하지 않는다.
- `createGameView`는 실제 필요한 구단만 복사한다. 공식 일정은 리그별로 한 번 인덱싱하며, 이미 준비된 커리어 달력을 다시 준비하지 않는다.
- 커리어 GET은 요청 안에서 새로 파싱한 상태를 보정한다. 같은 저장 전체를 추가 복제하지 않는다. 호환 타석 이동은 cursor만 복사하며 선수/계약 projection을 다시 쓰지 않는다.

## 검증과 재현

`node scripts/profile-match.mjs 46bce4204a21467ba4e54988c5229fc052e8ecf7`로 직전 소스와 현재 소스를 비교한다. 합성 seed 407, 롯데, 정규 길이 프리시즌의 같은 입력을 사용하며 사용자 저장을 읽지 않는다.

한 로컬 Node 실행에서는 99이벤트·7:20의 결과를 유지하면서 엔진 생성 평균 2.22→0.004ms, 호환 타석 명령 전체 142.98→0.078ms, 완료 5.43→2.02ms였다. 전체 결과를 먼저 계산하므로 시작은 1.89→3.57ms가 됐다. 수치는 환경마다 달라지며 **Workers CPU 계측이나 Free 한도 보증이 아니다**. 반복 실행 수 제거는 시뮬레이터 호출 횟수 테스트로 별도 검증한다.

자동 테스트는 한 번 생성·읽기/재생 비계산·성적 지연 반영·변경 전 이벤트 보존·투수/벤치 교체·재출전 거부·잘못된 버전/위치·상한·D1 재요청/충돌·동일 결과 아카이브를 검사한다. 브라우저에서 프리뷰 변경, 재생 중 POST 0건, 경기 중 변경 후 과거 10타석 유지·미래 변경과 재접속을 확인했다. 최종 테스트 수와 배포/기존 커리어 비교 결과는 [WORKLOG](../WORKLOG.md)를 따른다.
